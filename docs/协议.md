# 信封协议 v1

一句话：**一个 JSON 文件，里面装着 AES-GCM 加密的配置，外面套一层 ECDSA 签名，带一个单调递增的 seq。**

发布端 `tools/publish.mjs`，消费端 `app/src/.../Envelope.java`。两端必须一致，
所以这份文档是唯一的依据——改协议就改这里，两边一起改。

---

## 1. 信封结构

```json
{
  "v": 1,
  "alg": "A256GCM+ES256",
  "kid": "k1",
  "seq": 42,
  "iat": 1792318884,
  "n1":   "base64url(12B)",   // 包 DEK 用的 nonce
  "wdek": "base64url(48B)",   // 被 KEK 包住的 DEK：32 密文 + 16 tag
  "n2":   "base64url(12B)",   // 包正文用的 nonce
  "ct":   "base64url(n+16)",  // 正文密文 + 16 tag
  "sig":  "base64url(DER)"    // ECDSA-P256-SHA256
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `v` | int | 协议版本，当前固定 `1` |
| `alg` | string | 固定 `A256GCM+ES256`，标识"GCM 加密 + ECDSA-P256 签名" |
| `kid` | string | 密钥标识。参与 HKDF 的 salt，换 kid 等于换一把密钥；也参与 AAD |
| `seq` | int | 单调递增序号。防回滚的唯一依据，见 §5 |
| `iat` | int | 签发时间（Unix 秒）。仅用于审计，**不参与过期判断**（电视时钟不可信） |
| `n1` | b64u | DEK 包的 GCM nonce，每次发布随机 12 字节 |
| `wdek` | b64u | `AESGCM(KEK, n1, DEK)`，48 字节 |
| `n2` | b64u | 正文的 GCM nonce，每次发布随机 12 字节 |
| `ct` | b64u | `AESGCM(DEK, n2, payload)` |
| `sig` | b64u | DER 编码的 ECDSA 签名（Node 与 Java 都默认 DER，无需转换） |

编码统一 **base64url、无 padding**（Node `base64url`，Android `Base64.URL_SAFE | NO_WRAP`）。

---

## 2. 密钥

两把独立密钥，职责不能混：

```
主密钥 master   32 字节随机。构建期注入 APK（masterB64），也用于发布端。
签名密钥对      ECDSA P-256 (prime256v1)。私钥只在构建机；公钥 91 字节 DER 钉进 APK。
```

`master` **不是**直接当 AES 密钥用，而是先派生：

```
KEK = HKDF-SHA256(ikm = master, salt = utf8(kid), info = "chai-config-kek-v1", L = 32)
```

`DEK` 是**每次发布随机生成的 32 字节**，只用来加密本次正文。

### 为什么要 KEK 包 DEK，而不是直接用 KEK 加密正文

因为这样"换密钥"和"换内容"解耦了：换 `master`/换 `kid` 只需要重新封装那 48 字节的 `wdek`，
正文密文不用重新生成。这也是将来若要改成"口令派生 KEK"时唯一需要动的代码位置。

代价是每次发布多 48 字节和一次 GCM 运算——对 1.5 KiB 的信封无所谓。

---

## 3. 加密

两段 GCM，AAD 都绑定 `kid` 与 `seq`：

```
wdek = AES-256-GCM(key = KEK,  nonce = n1, aad = "chai-config-v1|wrap|"    + kid + "|" + seq, pt = DEK)
ct   = AES-256-GCM(key = DEK,  nonce = n2, aad = "chai-config-v1|payload|" + kid + "|" + seq, pt = payload_json)
```

密文与 16 字节 tag 直接拼接（`ciphertext || tag`），所以 `wdek` 恒为 48 字节。

**AAD 里塞 kid 和 seq 的作用是防止跨信封搬运**：把 A 信封的 `ct` 塞进 B 信封，
即使两者恰好用同一把 DEK，AAD 不匹配也会立刻失败。

**nonce 必须每次发布随机**。同一把密钥 + 同一 nonce = 密钥流复用 = 明文可被恢复。
**绝对不要**图省事拿 `seq` 当 nonce——那正好制造出确定的 nonce 复用。

---

## 4. 签名

签名输入**不是** JSON 原文，而是逐字段换行拼接的规范化字节串：

```
chai-config-v1 \n 1 \n A256GCM+ES256 \n <kid> \n <seq> \n <iat> \n <n1> \n <wdek> \n <n2> \n <ct>
```

（`\n` 为真正的换行符，UTF-8 编码，无尾随换行。）

然后 `ECDSA-P256-SHA256` 签名，DER 编码，base64url 放进 `sig`。

### 为什么不能直接签 JSON 文本

键序、缩进、数字格式、Unicode 转义在两端不一致，就会出现"本地验得过、电视上验不过"的
偶发失败。这类 bug 只在特定内容下触发（比如某个别名里带了个需要转义的字符），
排查成本极高。规范化拼接把这个问题从根上消掉。

注意 `seq` / `iat` 是数字，序列化时用十进制无前导零（Node 的 `String(n)` 与 Java 的
`long` 拼接结果一致）。

## 5. seq 与防回滚

| 变量 | 存在哪 | 含义 |
|---|---|---|
| `last_seq` | `sync_settings` prefs | 已接受过的最大 seq。**只增不减** |
| `applied_seq` | `sync_settings` prefs | 已真正写进 `server_configs` 的 seq |
| `cached_seq` | `sync_settings` prefs | 已验签解密、尚未应用的 seq |

规则：`seq <= last_seq` → 拒绝，原因码 `rollback`。

发布端 `nextSeq()` 自动读 `--out` 里已有信封的 `seq` 再 +1；
显式传 `--seq` 且不大于旧值时会直接报错退出，避免手滑。

**为什么要这一层**：签名只保证"这段内容是我签发过的"，不保证"是我此刻想让你用的"。
攻击者（或一个行为异常的镜像）可以把你三个月前签过的旧信封原样返回——签名合法、
AEAD 通过、客户端会正常回滚到旧账号。防回滚是唯一能挡住它的东西。

---

## 6. 校验顺序

```
① 结构/版本/算法
② 验签（ECDSA，公钥钉死）
③ 防回滚（seq > last_seq）
④ HKDF 派生 KEK → 解包 DEK
⑤ 解正文 → JSON 解析 → 内外 seq 一致
```

**不可颠倒**。先验签再解密，保证任何解密动作只发生在"已确认来源"的数据上。
反过来说，如果先解 `wdek` 再验签，你就把 GCM 解密当成了一个不可信的解析器在用，
攻击者可以构造海量畸形输入，在解密与异常路径上消耗电量甚至触发实现缺陷。

每一步失败都抛 `Envelope.Reject`，`code` 直接落进 `sync_status.txt`：

| 步骤 | 原因码 |
|---|---|
| ① | `bad-json` / `bad-version` / `bad-alg` |
| ② | `bad-signature` |
| ③ | `rollback` |
| ④ | `bad-master` |
| ⑤ | `bad-ciphertext` / `bad-payload` / `seq-mismatch` |

## 7. 轮换

| 换什么 | 要重新封装 | 要重打包 APK | 说明 |
|---|---|---|---|
| 正文内容（账号 / token） | ✅ | ❌ | 日常路径 |
| `kid` | ✅ | ❌ | `kid` 是从信封里读的，不在 APK 里。换 `kid` 等于换一把 KEK，**可以热换** |
| `master` | ✅ | ✅ | `master` 编译进 APK，必须重打包 |
| 签名密钥对 | ✅（用新私钥重签） | ✅ | 公钥 DER 钉在 APK 里 |

一句话：**密钥类改动里，只有 `kid` 能热换；`master` 和签名密钥都必须重打包。**

## 8. 兼容性约束（minSdk 23）

改实现时容易踩的三个坑：

| 想用的 | 实际限制 | 替代 |
|---|---|---|
| `java.util.Base64` | API 26+ | `android.util.Base64` + `URL_SAFE \| NO_WRAP` |
| `Signature.getInstance("Ed25519")` | API 33+ | `SHA256withECDSA` |
| `String.join` | API 26+ | `StringBuilder` |
| 内置 HKDF | 无 | 手写 20 行（`Envelope.hkdf`） |

`GCMParameterSpec` 是 API 21，安全。

## 9. 正文语义（accounts）

信封解出来的 JSON 不是随便的账号数组，下面五个字段决定母 APK 怎么合并：

| 字段 | 类型 | 含义 |
|---|---|---|
| `servers` | array | 本次要 upsert 的服务器。`partial=false` 时它同时是“完整清单” |
| `partial` | bool | `true` = 只更新 `servers` 里的条目；**不删除**电视上其它已管理服务器 |
| `orderIds` | array | 子 APK 里的完整服务器顺序。母 APK 按它重写 `server_order`；不在 `result` 里的 id 会被忽略 |
| `removedIds` | array | 显式要删除的服务器 id。无论 partial 与否都生效 |
| `lastUsedServerId` | string | 建议的默认服务器。电视本地已有有效 `last_used_server` 时**本地优先**，云端不覆盖 |

规则：

```
partial=false → 电视上的 managed_ids 与 servers 做差集，未出现的会被删除（旧行为）
partial=true  → 只 upsert；managed_ids 取并集；显式 removedIds 仍然删除
orderIds     → 无论 partial 与否，都按它重写 server_order（后面补 result 里剩余的 id）
```

`partial` 是给“子 APK 只勾选了一部分服务器”用的。没有它，部分推送会被母 APK 误判成
“这些是全部账号”，把未勾选的服务器从电视上删掉。

`orderIds` 是给子 APK 的“上移/下移”用的：`servers` 只包含勾选项，未勾选项不在里面，
所以不能靠 `servers` 的数组顺序表达完整排序。母 APK 只把 `orderIds` 当作**顺序提示**，
不会因为某个 id 不在 `servers` 里就删除它。

`lastUsedServerId` 只在电视本地没有有效选择时生效。否则每次后台同步都会把用户在
原 App“切换服务器”弹窗里手动选的服务器顶回去。

## 10. 已知不做的事

- **不处理时钟**。`iat` 只做审计，不参与有效性判断。电视系统时间经常是错的，
  任何基于时间的过期判断都会变成"莫名其妙不更新"。
- **不做压缩**。信封 1.5 KiB，压不压缩无所谓；加了反而给解压炸弹留口子。
- **不支持多信封/多份配置**。一个仓库一个信封，`seq` 全局单调。
  要多套配置就开多个仓库，各自独立密钥。
